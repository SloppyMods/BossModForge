# BossModForge — Implementation Plan (builder handoff)

The spec (`docs/specs/2026-09-18-bossmodforge-design.md`) is authoritative on *what*; this plan is the *order* and the *acceptance criteria*. Milestones are tracer bullets: each ends with something runnable end-to-end, even if thin.

## Ground rules for builder agents

1. **Resolve `VERIFY` before coding a section.** Read the upstream file at the pinned commit, then edit the spec in place with the confirmed value and remove the tag. Record the commit hashes in `docs/UPSTREAM.md`.
2. **Core never references Dalamud, ImGui, or BossMod.dll.** If you need a Dalamud type in Core, you have the seam wrong — add an interface in Core and implement it in Plugin.
3. **Tests before inference.** Every inference stage gets golden tests: fixture recording(s) → expected EM fragment. Start with *synthetic* recordings generated by a fixture builder (`Tests/Fixtures/RecordingBuilder`) so tests do not depend on real game logs; add real logs (user-supplied, `.gitignore`d, path via env var) as a second tier.
4. **Determinism.** Same inputs + options → byte-identical EM JSON and C#. Sort everything; no `Dictionary` iteration order leaks; timestamps serialised as ISO-8601 UTC.
5. **Confidence is mandatory.** A stage that cannot compute confidence emits `Low` + a `review` item; it never omits the field.
6. **No custom BossMod components in emitted code.** If a mechanic does not map to the table in spec §7.3, emit a `Review` and a comment block.
7. Follow repo conventions: `Dalamud.NET.Sdk/15.0.0`, `net10.0-windows10.0.26100.0` for the plugin, ECommons `Svc` accessor, game-state access only in `Framework.Update`, `quality-gate.json`, update `AGENTS.md` when folder purpose changes.
8. Keep any scratch/verification files outside the repo (`/tmp`) and delete anything you did put in.

## Milestones

### M0 — Skeleton + parser (tracer: `forge ingest x.log` prints op counts)

Tasks
- Create solution/projects per layout; CI script `scripts/build.sh` running `dotnet build` + `dotnet test`.
- Implement `Replay/`: magic detection, Brotli, `BinaryInput`/`TextInput` readers, `VER ` header, all tags in spec §4.2 as typed `Op` records, unknown tags → `RawOp`. `ActorTimeline.PosRotAt(t)`.
- `Tests/Fixtures/RecordingBuilder`: fluent API to synthesise text-format recordings (actors, moves, casts, effects, statuses, icons, tethers, envc, zone, party, combat flags) with a controllable clock.
- CLI `ingest`.

Acceptance
- Parses a synthetic text recording and a synthetic binary (uncompressed + Brotli) recording produced by the same builder → identical op streams.
- Parses a real BossMod recording supplied via `FORGE_REAL_LOGS` env var with zero exceptions and < 1 % `RawOp` for supported versions (skipped if env var unset).
- Conformance stub: CLI subcommand `conform` that, when `--bossmod-dll` is given, loads BossMod's parser via reflection and compares op counts per tag (may be a later milestone if reflection is painful; document the choice).

### M1 — Segmentation + catalog + enums + trivial module (tracer: `forge infer && forge emit` yields a compiling `TrivialPhase` module)

Tasks
- `PullSegmenter`, `ParticipantClassifier`, `AbilityCataloger` (incl. cast↔effect matching window, statuses/tethers/icons tables).
- `IGameData` + `LuminaGameData` (CLI, `--game-path`); name → C# identifier sanitiser with dedupe.
- `EncounterModel` v1 + JSON schema + serializer (deterministic ordering).
- `ModuleEmitter` with `BmrProfile` and `VbmProfile` producing enums + `TrivialPhase()` states + `[ModuleInfo]` module with placeholder `ArenaBoundsCircle(20)`; `FORGE.md`.
- Resolve `VERIFY`: Helper OID, `ModuleInfo` attribute shape per flavor, enum conventions.

Acceptance
- Synthetic 2-pull recording → EM with 2 pulls, boss/helper/add roles, ability table with instance counts matching the fixture.
- Emitted module compiles inside the pinned BMR checkout and the pinned vbm checkout (manual step documented in `docs/UPSTREAM.md`; automate in M4).
- Golden test: fixture → EM JSON → C# text, byte-exact.

### M2 — Arena bounds + shape inference (tracer: emitted `SimpleAOEs` with fitted shapes)

Tasks
- `BoundsFitter` (§5.8) with snapping and per-phase change detection.
- `OmenParser` (fan angle, weak donut prior) with a table-driven test corpus.
- `ShapeInference` (§5.4): sheet prior table, δ search, circle/donut/cone/rect/cross fitters, raidwide detection, scoring, snapping, evidence.
- Emit `SimpleAOEs`/`SimpleAOEGroups`/`RaidwideCast` from `TelegraphedAOE|HiddenAOE|Raidwide` classes only (rest in M3).

Acceptance
- Unit tests per fitter: given planted shape + random player positions (seeded), recover parameters within 0.5 y / 3° in ≥ 98 % of 200 seeds; ambiguous cases (margin < 1 y) produce `Medium/Low` not `High`.
- δ search picks the planted snapshot lag within 0.1 s.
- Arena fit recovers planted circle/square within snapping tolerance; polygon fallback triggers for an L-shaped fixture.

### M3 — Mechanic classification + component mapping

Tasks
- `MechanicClassifier` rules (§5.5) with rule ids in evidence; bait-rule detection (nearest/farthest).
- Knockback distance/direction from effect entries + displacement check; gaze via facing; spread/stack via icons + falloff; tankbuster via target/damage heuristics; interrupt flag; chasing detection.
- Extend emitter for the full table in §7.3 across both profiles. Resolve component-name `VERIFY`s.

Acceptance
- One synthetic fixture per mechanic class → expected class and expected component snippet (golden).
- Negative tests: a raidwide is not classified as tankbuster; a stack with 1 hit is `Low`.

### M4 — Timeline alignment, phases, state machine + validation harness

Tasks
- `TimelineAligner` (progressive NW alignment, gap stats, support), loop folding, `PhaseDetector` cues, branch detection.
- Emit `Cast/CastMulti/Timeout/Targetable/ComponentCondition` chain with `ActivateOnEnter/DeactivateOnExit` placement, phase methods, state id scheme. Resolve builder-API `VERIFY`s.
- `forge validate`: copy module into checkout scratch namespace, `dotnet build`, run `ReplayValidator` host (template project in `Cli/ReplayValidator/` instantiated into the checkout), collect transition timings and AOE precision/recall, write `validation-report.{json,md}`, map compile errors back to EM items.
- Parser conformance test wired into `validate`.

Acceptance
- Synthetic 3-pull recording with a planted 6-step rotation loop and one branch → consensus with correct order, support counts, loop bounds, and MAD; timing jitter fixture → `Timeout` + `Review`.
- `forge validate` on the synthetic fixture (converted to BossMod's text format — the fixture builder already emits it) passes with p90 ≤ 1.0 s and AOE P/R = 1.0. Exit codes per spec §10.
- Running `validate` on a deliberately wrong radius yields recall < 0.95 and a downgraded EM confidence.

### M5 — Dalamud plugin UI

Tasks
- Plugin scaffold (`Plugin.cs`, `Configuration.cs`, `/forge`), `DalamudGameData`, `ReplayDiscovery` (BossMod + BMR replay dirs), `AnalysisRunner` (background task, progress, cancel, immutable snapshots).
- Windows per spec §9; `EvidencePlot` (angle/dist scatter + fitted shape overlay; top-down instance view reusing MarkerMind's minimap renderer approach).
- Overrides editing (shape/mechanic/enum name/ignore) persisted into EM `overrides`; re-emit without re-analysis.
- Export tab: EM JSON, C#, clipboard, open folder, show last validation report.
- BossMod IPC presence check (pattern from `MarkerMind/Core/Adapter/BossmodBridge.cs`).

Acceptance
- Analyze a real recording in-game with no frame hitches > 16 ms attributable to Forge (measure with a stopwatch around `Framework.Update` work; heavy work must be off-thread).
- Change a shape override in UI → re-emit → C# reflects it; inference re-run does not clobber it.

### M6 — Multi-recording merge + robustness

Tasks
- `forge merge` / plugin "Add recordings to encounter": merges instances, recomputes fits and alignment, preserves overrides.
- Degraded-version parsing path; large-file streaming (do not hold raw bytes of a 200 MB log twice).
- Door-boss / adds-phase / trash-filter fixtures.

Acceptance
- Merging 1-pull + 2-pull recordings yields the EM of concatenating them and analysing once, modulo `sources[]` (the concatenated op stream drives analysis; `sources[]` lists one entry per input recording; pulls are segmented per recording and concatenated; actor instance ids must be distinct across recordings — fixtures guarantee this; the real-world collision caveat is recorded in FORGE.md output).
- 200 MB synthetic recording parses under 10 s and < 1 GB peak (CLI, release build).

### M7 — Optional LLM polish pass (ADR-007)

Tasks
- `forge polish <em.json> --provider …`: prompt = EM + evidence summaries + review items; the model returns *EM edits only* (JSON patch limited to `enumName`, `name`, `comment`, choosing among `suggested[]` for review items). Schema-validated; rejected patches logged.

Acceptance
- Patch that touches any field outside the allowlist is rejected with a clear error; polish is fully skippable and never required for `validate`.

## Definition of done (project)

- All milestones' acceptance criteria pass in CI (`scripts/build.sh`).
- A real unmodded encounter recording (user-supplied) → `forge infer → emit → validate` passes with zero `High` review items **or** the remaining review items are each explained in `FORGE.md`.
- `AGENTS.md`, `CONTEXT.md` (glossary from spec §0), `README.md` (build/run), `docs/UPSTREAM.md` (pins) are current; `quality-gate.json` present.

## Suggested parallelisation for multiple builder agents

- Agent A: M0 parser + fixture builder (blocks everyone; do first, small surface).
- After M0: Agent B — M1 segmentation/catalog/EM/emitter skeleton; Agent C — M2 fitters (pure math, only needs `Recording` + `ActorTimeline` + `IGameData`).
- After M1+M2: Agent D — M3 classifier; Agent E — M4 aligner + validate harness (needs pinned checkouts).
- After M4: Agent F — M5 plugin UI (needs stable EM + runner API).
- M6/M7 anyone.

Interfaces that must be frozen early so agents can work in parallel: `Recording`/`Op` records and `ActorTimeline` (M0), `IGameData` (M0), `EncounterModel` v1 + `Confidence`/`Evidence` (M1 start), `IEmitterProfile` (M1).
